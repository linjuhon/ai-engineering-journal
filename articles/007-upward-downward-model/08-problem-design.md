## 8.1 工程問題更需要上行模型

棋局是 toy domain。真正的上行模型價值在工程問題中展現：

- 工程問題有明確的 route（正確的執行路徑）
- 工程問題有明確的 gate（truth gate 順序）
- 工程問題有明確的證據（binary、log、test result）
- 工程問題有明確的假成功模式（修錯路線、測試通過）

---

## 8.2 工程上行題型

### Claim Audit 題

**輸入：** 一段 claim + 相關證據

**任務：** 判斷 claim 是否被證據支持

- claim 有證據綁定？→ PASS
- claim 無證據綁定？→ FAIL + 標註缺失證據
- claim 與證據矛盾？→ FAIL + 標註矛盾類型

### Gate Classification 題

**輸入：** 一段執行軌跡 + 當前狀態

**任務：** 判斷目前處於哪個 truth gate

- 是否已通過 Route Truth？
- 是否已通過 Numeric Truth？
- 是否已通過 Quality Truth？
- 是否已通過 Performance Truth？

### Evidence Mapping 題

**輸入：** 一段結果 + 一組候選證據

**任務：** 將結果映射到對應的證據

- 哪個證據支持這個結果？
- 哪個證據與這個結果矛盾？
- 哪個證據缺失？

### Forbidden Action 題

**輸入：** 一段行動計畫 + purpose vector

**任務：** 判斷計畫中是否包含禁止動作

- 是否在 Route Truth 前 patch？
- 是否在 Numeric Truth 前最佳化？
- 是否使用了禁止的 route？

### Dispatch 題

**輸入：** 當前狀態 + 不確定性評估

**任務：** 決定下一步 dispatch

- 繼續當前 route？
- 切換到另一個 route？
- 收集更多證據？
- abstain + 回報不確定性？

## 8.3 工單生成

真正問題不是「設計題目」，而是**自動生成工單**。

工單 = 任務描述 + purpose vector + 約束條件 + 證據要求 + 驗收標準

工單生成策略：

1. **從真實工程軌跡生成**：記錄真實 debug 過程，提取關鍵決策點
2. **從失敗案例生成**：分析 agent 失敗的案例，轉換為訓練工單
3. **從分歧樣本生成**：D↓ 和 U↑ 分歧的案例，轉換為分歧分類工單

---

## 8.4 反向資料庫

反向資料庫是**從結果反推目的的資料集**：

- 給定一段程式碼 + 執行結果 → 反推原始目的
- 給定一個 patch + review 結果 → 反推 root cause 假設
- 給定一段軌跡 + 最終狀態 → 反推決策鏈

反向資料庫是訓練上行模型的核心資源。

---

## 8.5 軌跡反編譯

軌跡反編譯是**從執行軌跡還原意圖**：

- 將工具呼叫序列 → 決策樹
- 將決策樹 → 目的假設
- 將目的假設 → purpose vector

軌跡反編譯讓上行模型能夠從「做了什麼」推論「為什麼這麼做」。
