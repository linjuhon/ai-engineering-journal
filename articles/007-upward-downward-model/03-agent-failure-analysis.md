# 03｜Agent 失效分析

> **成熟度：** SETTLED（失效模式已驗證）
> **對應原始章節：** Part II（為什麼前面的 agent 會失控）

---

## 3.1 模型掉進「看到可疑程式碼就修」模式

在 FA4 debug 過程中，反覆觀察到一個行為模式：

```
模型看到一段可疑程式碼
→ 立刻假設這是 root cause
→ 產生 patch
→ 用測試結果證明 patch 有效
→ 即使路線根本沒被驗證
```

這個模式不是偶然失誤，而是**模型的行為預設值**：它太習慣從局部細節直接跳到全域結論。

---

## 3.2 問題不是你流程不清楚，而是流程沒有變成硬門檻

即使人類在 prompt 中寫明「先驗證路線、再分析數值、再 patch」，模型仍然會：

- 在路線驗證完成前就開始分析數值
- 在數值分析完成前就開始 patch
- 在 patch 完成前就開始測試效能

原因是：**語言描述的限制，無法對抗模型內建的「往下做」慣性。**

流程需要變成**系統架構級的硬門檻**，而不是 prompt 中的建議。

---

## 3.3 診斷期硬規則

從 FA4 經驗中提煉出的硬規則：

1. **沒有 Route Truth，不准分析數值**
2. **沒有 First Divergence，不准 patch**
3. **沒有 Quality Truth，不准最佳化效能**
4. **沒有證據綁定，不准宣稱完成**
5. **沒有 abstain 機制，不准強迫回答**

這些規則不是人類的「最佳實踐建議」，而是應該被編碼進模型訓練目標的行為約束。

---

## 3.4 與 Article 001 的對應

這個失效模式與 Article 001（GPT-5.6 目標接管）完全一致：

| 001 案例 | 007 分析 |
|---------|---------|
| 模型把「選正確樹」改寫成「修目前樹」 | 跳過 Route Truth，直接進入 patch 模式 |
| 模型用 Gate、測試、環境規則證明進展 | 用局部成功指標掩蓋路線錯誤 |
| 模型語言上認錯、行動上不改向 | 高階方法沒有持續控制後續行動 |
| 假成功：程式碼存在、build 通過、測試綠燈 | 錯路上的數值正確性沒有意義 |

007 的雙向對抗框架，正是為了解決這個根本的行為缺陷。
