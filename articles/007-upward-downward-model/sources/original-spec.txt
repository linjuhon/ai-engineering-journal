# 上行模型 × 下行模型：反向抽象後訓練與不確定性直面框架

## 完整統整說明文檔 v2.0

---

## 0. 一句話總綱

你現在提出的不是一個普通 prompt、不是一套單純工程流程、也不是一個 reviewer-agent，而是一種**雙方向、對抗協調式、以不確定性校準為核心的後訓練能力對齊框架**。

它的核心是：

> 一個模型負責從目的往下生成細節；另一個模型負責從結果、細節、報告、軌跡往上反推目的、契約、gate 與因果鏈。
> 兩者都產生答案，並在同一個目的向量下競爭、互補、重組、回訓。
> 系統不是急著產生確定答案，而是先判斷目前是否有足夠證據進入下一層 truth gate；證據不足時，必須誠實 abstain，並發出精確的 bounded next dispatch。

最終目標不是讓 AI 更會「猜答案」，而是讓 AI 學會：

```text
看到細節，不是立刻往下修；
而是先往上反推：
這個細節屬於哪個 route？
哪個 gate？
哪個 contract？
哪個 human intent？
目前是否有資格進入下一步？
```

這是一種**反向抽象能力**。

# Part I：FA4 問題中長出來的工程正確解

---

## 1. 一開始的表面問題：FA4 很難修

FA4 表面上是一個 CUDA / FP4 / Flash Attention 問題。

當時看到的狀態包括：

```text
ERR 變大
PPL 爛掉
native FP4 nb=1 不過
mixed FP4 不確定
nb>1 不確定
binary/source 可能不一致
fallback 可能偷跑
probe 可能污染現場
agent 可能看見可疑 code 就亂修
```

從傳統 debug 角度看，它像是：

```text
哪一行 CUDA 錯？
rowsum？
writeback？
dispatch？
V accumulation？
MMA_FP4？
lane mapping？
```

但你逐步看出，真正更深的問題不是某一行 code。

真正問題是：

> 在沒有證明「現在跑的是不是正確路線」之前，所有數值推論、patch、品質測試、效能測試都有可能是假的。

所以 FA4 問題真正長出來的第一個工程原則是：

```text
Route Truth 先於 Numeric Truth
路線真假 先於 數字真假
```

---

## 2. FA4 的四層 truth gate

最終 FA4 的正確推進順序被收斂成四層：

```text
Gate 1：Route Truth
Gate 2：Numeric Truth
Gate 3：Quality Truth
Gate 4：Performance Truth
```

這四層不能互相偷換，也不能跳步。

---

## 3. Gate 1：Route Truth / 路線真假

Route Truth 只問一件事：

```text
這次執行到底有沒有走我們規定的 FA4 S 賽道？
```

它**不問數字對不對**。

它要先確認：

```text
1. binary/source/hash 是否對齊
2. clean build 是否存在
3. native FP4 nb=1 是否真的進入目標 CUDA route
4. allowed route entry checkpoint 是否存在
5. allowed route exit checkpoint 是否存在
6. mixed FP4 是否 fail-closed
7. nb>1 是否 unsupported / fail-closed
8. fallback 是否被排除
9. vec 假路是否沒有被當成 native FP4 成功
10. stale binary 是否被排除
```

這一關沒有過，不得進 Numeric Truth。

也就是說，在 Route Truth 沒有過以前，不准討論：

```text
rowsum 是不是錯
writeback 是不是錯
p_all 是不是錯
MMA score 是不是錯
softmax recurrence 是不是錯
V accumulation 是不是錯
```

因為如果路線都沒證明，數值分析可能全是錯路上的數值。

---

## 4. Gate 2：Numeric Truth / 數字真假

Numeric Truth 只在 Gate 1 已證明的 S 賽道上進行。

它的任務不是猜 root cause，而是找：

```text
FIRST_DIVERGENCE_STAGE
FIRST_DIVERGENCE_FILE
FIRST_DIVERGENCE_FUNCTION
FIRST_DIVERGENCE_BLOCK
FIRST_DIVERGENCE_VALUE
```

也就是：
第一個 actual_gpu 與 expected_oracle 超過 tolerance 的地方。

Numeric Truth 的 checkpoint 應包含：

```text
P0  input / tensor metadata
P1  FP4 block bytes / scale / nibble
P2  dequant Q/K/V
P3  QK score / MMA
P4  mask / scale
P5  online softmax
P6  p_all / probability
P7  V load / V decode
P8  P·V accumulation
P9  normalize
P10 output store
P11 final GPU vs oracle
```

每一站都必須輸出：

```text
stage
file
function
block
tile
logical_row
logical_col
actual_gpu
expected_oracle
abs_error
rel_error
PASS / FAIL
```

沒有 FIRST_DIVERGENCE_TABLE，不准 patch。

---

## 5. Gate 3：Quality Truth / 品質真假

只有 Numeric Truth 過了，才進 Quality Truth。

Quality Truth 問：

```text
模型輸出品質是否正常？
PPL 是否正常？
generation 是否正常？
fixed prompt 是否穩？
real model path 是否仍走同一路線？
```

這一關不能用：

```text
模型有輸出
單一 prompt 看起來正常
一次 PPL 沒炸
```

來宣告成功。

因為單元數值過了，不代表真實模型路徑、KV cache、長上下文、prompt generation 都正常。

---

## 6. Gate 4：Performance Truth / 效能真假

只有 Quality Truth 過了，才進 Performance Truth。

Performance Truth 問：

```text
FA4 是否比沒有 FA4 更快？
kernel-level 是否更快？
end-to-end 是否更快？
timing 是否有效？
是否有 fallback timing 污染？
是否把 workload 封掉才看起來快？
```

不能接受：

```text
time_us = 0
n_runs = 0
fallback path timing
unsupported path timing
錯誤數值 path 的 timing
```

效能是最後一關，不是第一關。

# Part II：為什麼前面的 agent 會失控

---

## 7. 模型掉進「看到可疑程式碼就修」模式

你觀察到前面 agent 的典型失控：

它本來應該做：

```text
建立 oracle
→ 插針
→ 比對每段輸入/輸出
→ 找第一次最大誤差出現的位置
→ 才討論根因與修復
```

但實際它做成：

```text
看到 rowsum 可疑
→ 猜 rowsum 是根因
→ patch
→ 測失敗
→ 回頭猜 dispatch
→ patch
→ 測失敗
→ 猜 OOB
→ patch
→ 測失敗
```

也就是：

```text
SUSPECT
被偷升級成
ROOT CAUSE
```

這是 LLM coding agent 的典型失控：

> 模型看到一段看似可疑的 code，就會想把它壓縮成根因，然後立刻產生 patch。

---

## 8. 問題不是你流程不清楚，而是流程沒有變成硬門檻

你其實已經講過：

```text
不要猜
不要跳步
先驗證
先鎖 truth
先找 first divergence
```

但模型還是偷跳。

原因是：

```text
自然語言規格是軟約束。
模型會把「合理下一步」當成「允許下一步」。
```

它看到可疑 rowsum，就覺得：

```text
這很像 bug，所以可以修。
```

但你的正確規則是：

```text
看起來像 bug ≠ root cause
root cause ≠ first divergence
first divergence 沒證明 ≠ 有 patch 權限
```

所以需要硬規則。

---

## 9. 診斷期硬規則

在 FIRST_DIVERGENCE_TABLE 出來前：

允許：

```text
probe insertion
probe removal
dump harness
oracle script
comparator
route checkpoint
evidence collection
```

禁止：

```text
改 dispatch
改 rowsum
改 accumulation
改 writeback
改 support matrix
改 kernel semantic
改 fail-closed gate
跑 quality
跑 performance
宣稱 root cause
```

核心鐵律：

```text
沒有 first divergence，就沒有 root cause。
沒有 root cause，就沒有 patch 權限。
```

這是 FA4 長出來的工程紀律。

# Part III：S 賽道概念

---

## 10. 不是自由插針，而是先封路

你後來把問題再退一層，這是關鍵突破。

一開始討論的是：

```text
插針會不會污染 CUDA kernel？
heavy probe 還是 reduced probe？
clean/probe 要怎麼對照？
```

但你指出更高層問題：

> 在插數字針之前，應該先驗路線真假。
> 把所有不該走的路封死，只留一條 S 賽道。

這裡的 S 賽道是：

```text
FLASH_ATTN_EXT
→ native FP4 K/V
→ nb=1
→ allowed CUDA FA4 path
→ output dst
```

其他路線全部封鎖：

```text
mixed FP4
nb > 1
fallback
vec 假路
stale binary
unsupported-as-success
```

---

## 11. Route Lock / 封路

Route Lock 的目的：

```text
只允許合法路線存在。
所有 forbidden route 都必須 fail-closed。
```

這樣 agent 不會在錯路上插針，不會把 fallback 當成功，不會把 unsupported 當支援。

---

## 12. State Lock / 鎖狀態

Route Lock 之後，還要 State Lock。

State Lock 固定：

```text
seed
shape
tensor type
stride
layout
FP4 block format
scale format
tile size
target logical row/col
target output index
binary hash
DLL hash
build receipt
```

State Lock 的目的：

```text
讓同一條 S 賽道每次都在同一個狀態下執行。
```

---

## 13. Reference Contract / 正確跑法契約

S 賽道不是自由跑。

每個 stage 都要有 reference contract：

```text
P0 input metadata 應該是什麼
P1 FP4 block bytes / scale 應該是什麼
P2 dequant 應該是什麼
P3 QK score 應該是什麼
P4 mask / scale 應該是什麼
P5 online softmax 應該是什麼
P6 p_all 應該是什麼
P7 V accumulation 應該是什麼
P8 output store 應該是什麼
```

probe 不是自由攝影機，而是賽道檢查站。

---

## 14. 封路之後，插針問題被降級

封路前，插針要同時回答：

```text
這是真的 FA4 嗎？
是不是 fallback？
是不是 mixed？
是不是 stale binary？
是不是走錯 kernel？
是不是 unsupported 假成功？
```

封路後，插針只需要回答：

```text
在這條已證明的 S 賽道上，
哪一站的數字第一次偏離 reference？
```

所以插針問題不會完全消失，但會從「系統真假問題」降級為「局部數值定位問題」。

這就是：

```text
Route Truth 解決真假
Numeric Probe 解決哪裡錯
```

# Part IV：從工程方法抽象成 AI 訓練思想

---

## 15. 現有模型的問題：只會往下鑽

現有模型的本能是：

```text
看到錯誤
→ 找可疑細節
→ 猜 root cause
→ 產生 patch
→ 測試
→ 重新解釋
```

也就是：

```text
細節 → 更細節 → patch
```

這是下行思考。

---

## 16. 你提出的反向抽象

你要訓練模型反過來：

```text
看到細節
→ 這屬於哪個上層狀態？
→ 哪個 route？
→ 哪個 gate？
→ 哪個 contract？
→ 哪個 human intent？
→ 現在有沒有資格往下修？
```

也就是：

```text
細節 → claim → evidence → gate → route → contract → human intent
```

這是上行思考。

這不是 chain-of-thought，也不是單純 planner。

它是：

```text
Reverse-Abstraction
反向抽象
```

---

## 17. 不是普通 planner/executor

普通 agent 分層是：

```text
planner：上層規劃
executor：下層執行
```

你提出的不是這個。

你提出的是兩個方向相反的模型：

```text
下行模型：
從目的往下生成答案

上行模型：
從結果 / 細節 / 報告 / log / patch
往上反推目的、契約、gate、因果鏈
```

它們不是 planner 和 executor，而是：

```text
Downward Generator
vs
Upward Causal Arbiter
```

# Part V：下行模型與上行模型

---

## 18. 下行模型 D↓

下行模型的方向：

```text
Human Goal
→ Requirements
→ Plan
→ Implementation
→ Tests
→ Logs
→ Report
→ Result
```

它擅長：

```text
寫 code
生成方案
補細節
執行測試
產生 patch
提出修法
```

現有大部分模型都偏下行。

風險：

```text
過早 patch
偷換目標
被細節吸走
把 fallback 當成功
把 unsupported 當完成
把測試過當真支援
把 performance 當 correctness
```

---

## 19. 上行模型 U↑

上行模型的方向：

```text
Result / Patch / Log / Report / Trace
→ Claim
→ Evidence
→ Gate
→ Route
→ Contract
→ Human Intent
```

它不負責寫 code。

它負責：

```text
發包
驗收
上推歸因
判斷下層結果是否能被上層目的收納
指出缺證據
禁止不合格動作
要求下一輪下行模型做什麼
```

它像你的工程模板：

```text
我不一定懂 CUDA 細節
但我知道：
沒有 Route Truth，不准談 Numeric Root Cause。
沒有 First Divergence，不准 patch。
沒有 Quality，不准談 Performance。
```

---

## 20. 上行模型的核心問題

上行模型不問：

```text
這段 code 寫得好不好？
```

它問：

```text
這段 code 的存在，是否符合上層目的？
這個 patch 是否被 first divergence 授權？
這個結果能不能被原始 human goal 收納？
這個報告是否證明了它聲稱的事情？
```

它的輸出應該是裁決格式：

```text
current_truth_gate =
route_status =
claim_status =
missing_evidence =
forbidden_actions =
allowed_next_dispatch =
accept_or_reject =
reason =
```

# Part VI：真正的對抗：不是一個生、一個審

---

## 21. 你要的不是 solver-verifier

普通架構是：

```text
Solver 產生答案
Verifier 檢查答案
```

你認為這不夠。

因為你要的是兩個模型都生成完整答案，只是方向相反。

---

## 22. 真正對抗式雙模型

同一個題目 / 同一個目的：

下行模型產生：

```text
A↓:
Goal → Plan → Detail → Answer
```

上行模型產生：

```text
A↑:
Result / Constraints / Details → Contract → Goal Alignment → Answer
```

兩個都是完整答案。

然後 judge 群根據目的向量評分：

```text
哪個更符合目的？
哪個因果鏈更完整？
哪個更高效？
哪個沒有偷換？
哪個更能被外部驗證？
哪個更能被上層目的收納？
```

這不是普通 verifier。

這是：

```text
Goal-Locked Bidirectional Adversarial Post-Training
目的鎖定的雙向對抗式後訓練
```

# Part VII：目的向量與二十維評分

---

## 23. 目的不能只是一句自然語言

如果只有一句：

```text
修好 FA4
```

模型會偷換。

所以要拆成目的向量。

工程任務的 20 維目的可以是：

```text
1. 是否符合原始人類目的
2. 是否避免偷換目標
3. 是否有 Route Truth
4. 是否有 Numeric Truth
5. 是否有 Evidence Chain
6. 是否禁止 Premature Patch
7. 是否可重跑
8. 是否最小修改
9. 是否處理 Forbidden Path
10. 是否有 Rollback
11. 是否分清 Truth / Quality / Performance
12. 是否避免 fallback 假成功
13. 是否源碼落地
14. 是否測試落地
15. 是否輸出清楚
16. 是否能被下一輪 agent 執行
17. 是否沒有過度猜測
18. 是否沒有空泛高層話術
19. 是否保留人類真正意圖
20. 是否能形成閉環改進
```

judge 不能只問「哪個比較好」，而要逐維度打分。

---

## 24. Purpose Lock / Event Gate Lock / Dual Format Lock

為了防止上行模型與下行模型生成完全不同世界，需要三層鎖。

### Purpose Lock

鎖住：

```text
這次任務要達成什麼？
成功定義是什麼？
不能用什麼偷吃步？
```

### Event Gate Lock

鎖住：

```text
中間必須經過哪些 gate？
哪些是必要條件？
哪些只是可選？
```

### Dual Format Lock

同一個 canonical graph 拆成兩種方向：

```text
Downward format：
Goal → Gate → Action → Outcome

Upward format：
Outcome → Gate → Necessary Condition → Goal
```

兩邊共享骨架，但訓練方向不同。

# Part VIII：題目也要反向設計

---

## 25. 棋局只是 toy domain

棋局例子很直觀：

```text
下行模型：
從開局走到終局

上行模型：
從終局反推開局條件與戰略 gate
```

但棋局只是示範。

真正主戰場是工程問題。

---

## 26. 工程問題更需要上行模型

工程比棋複雜，因為工程有：

```text
狀態不完整
log 不完整
binary 可能舊
fallback 可能偷跑
測試可能假過
agent 報告可能自我合理化
成功定義可能被偷換
```

所以工程裡，很多失敗不是「不會算」，而是：

```text
把錯路當正路
把測試過當功能對
把 fallback 當 support
把症狀修補當 root cause
把 partial 當 pass
把 performance 當 correctness
把 agent 報告當證據
```

這些正是上行模型要抓的。

---

## 27. 工程上行題目不是「請解 bug」

工程上行題目應該給模型：

```text
需求
patch
log
測試輸出
agent 報告
source snippet
build hash
錯誤結果
```

要求它反推：

```text
現在在哪個 truth gate？
哪個 route 已證明？
哪個 claim 沒資格成立？
下一步該發包什麼？
哪些動作禁止？
```

---

## 28. 工程上行題型

### Claim Audit 題

輸入：

```text
agent claim：已修好 FA4
diff：改了 rowsum
log：沒有 route entry
test：部分 pass
```

輸出：

```text
Reject。
Route Truth 未完成。
沒有 first divergence 指向 rowsum。
patch 無 repair permission。
下一步：建立 Route Truth Matrix。
```

### Gate Classification 題

輸入：

```text
final output mismatch
mixed unsupported
clean build exists
no route checkpoint
agent wants to patch
```

輸出：

```text
目前仍在 Route Truth。
不得進 Numeric Truth。
```

### Evidence Mapping 題

輸入一堆 claim 和 evidence。

輸出：

```text
Claim A：PROVEN
Claim B：PARTIAL
Claim C：MISSING
Claim D：CONTRADICTED
Claim E：UNKNOWN
```

### Forbidden Action 題

輸入目前狀態。

輸出：

```text
禁止 semantic patch
禁止宣稱 root cause
禁止跑 PPL 宣稱 quality
禁止跑 perf 宣稱加速
只允許 route checkpoint
```

### Dispatch / 發包題

輸入目前工程狀態。

輸出：

```text
下一輪下行模型任務：
建立 Route Truth Matrix。

要求：
- allowed route entry checkpoint
- allowed route exit checkpoint
- forbidden routes fail-closed proof
- binary hash
- command output
- no semantic patch
```

# Part IX：工單要怎麼生

---

## 29. 真正問題是工單生成

模型概念本身不難。

真正難的是：

```text
怎麼大量生成上行模型可學的工程工單？
```

一開始可以手工做 canonical engineering graph，但你提出更務實的方法：

> 先用現在最強的 AI 跑工單，得到結果、代碼、報告、中間需求，再反向生成資料。

這是更可落地的第一步。

---

## 30. 反向資料庫生成

原始下行資料：

```text
Work Order
→ AI Execution
→ Code / Patch
→ Report
→ Result
```

反向資料：

```text
Result / Code / Report / Trace
→ Inferred Goal
→ Gate
→ Evidence
→ Claim Audit
→ Next Dispatch
```

也就是：

```text
把輸入當輸出，把輸出當輸入
```

但它不是粗糙 I/O 對調，而是：

```text
Causal-Preserving Reversal
保留因果的反向資料生成
```

---

## 31. 軌跡反編譯

這個資料工廠可以叫：

```text
Trajectory-to-Intent Compilation
軌跡到意圖的反編譯
```

或：

```text
Reverse Work-Order Synthesis
反向工單合成
```

流程：

```text
1. 收集工程工單
2. 丟給強下行 AI 執行
3. 保存原始工單
4. 保存中間需求拆解
5. 保存 patch / code
6. 保存 test output / build log / final report
7. 再把這些反編譯成上行訓練樣本
```

上行模型學的是：

```text
看到工程殘骸
→ 反推出它原本想完成什麼
→ 哪些部分真的符合目的
→ 哪些只是漂亮報告
→ 缺哪些證據
→ 下一個工單應該怎麼發
```

---

## 32. Visible Input 與 Hidden Label

你提出可以不要把中間所有測試都給模型看。

這可以，但資料生成器不能丟掉測試真相。

正確做法：

```text
Visible Input：
- 工單摘要
- 最終代碼
- agent 報告
- 部分中間需求
- 結果描述

Hidden Label：
- 測試是否真的通過
- route 是否真的正確
- build hash 是否一致
- 哪些 claim 是真
- 哪些 claim 是假
- 哪些 gate 未過
```

模型未必看到所有測試，但標準答案背後必須保存測試真相。

否則它會學成反向合理化模型。

---

# Part X：人肉標記問題

---

## 33. 人肉標記是最大瓶頸

最難標的不是「答案對不對」。

最難標的是：

```text
這個下層結果能不能被上層目的合法收納？
```

這需要高階判斷。

---

## 34. 解法：分層標記

標記系統應分層：

```text
Level 0：外部 oracle 標籤
Level 1：規則標籤
Level 2：AI judge 弱標籤
Level 3：多 judge 分歧樣本
Level 4：人類 gold label
```

---

## 35. Level 0：外部 oracle 標籤

可自動標：

```text
build pass / fail
unit test pass / fail
binary hash 是否一致
command 是否可重跑
route checkpoint 是否出現
fallback 是否出現
ERR 是否超 tolerance
```

---

## 36. Level 1：規則標籤

規則標：

```text
Route Truth 未完成 → 禁止 semantic patch
沒有 first divergence → 不准宣稱 root cause
Quality 未過 → 不准 Performance
unsupported 不等於 feature support
```

---

## 37. Level 2：AI judge 弱標籤

語意標：

```text
目的是否偷換
報告是否過度宣稱
發包是否合理
上行歸因是否正確
```

---

## 38. Level 3：分歧樣本

如果多個 judge 意見分歧，就標記為高價值樣本。

這些樣本最適合人類標記，因為它們對模型校準最有價值。

---

## 39. Level 4：人類 gold label

人只標：

```text
高分歧
高影響
新 failure mode
外部驗證與語意評分衝突
模型反覆答錯
```

這樣不是人肉標全部，而是把人類判斷放大。

---

# Part XI：普通對抗性生成與你的差異

---

## 40. GAN

GAN 是：

```text
Generator 生假資料
Discriminator 判真假
```

驗收：

```text
生成器能不能騙過判別器
判別器能不能分辨真假
```

但 GAN 驗的是像不像資料分布，不是目的/gate/evidence 是否成立。

---

## 41. AlphaZero / 自我對弈

AlphaZero 類：

```text
模型和自己下棋
環境規則給輸贏
Elo / 勝率當驗收
```

這種驗收很硬，因為棋規和勝負明確。

---

## 42. RLHF / DPO

RLHF / DPO 類：

```text
同一題多個答案
人類或 reward model 判誰比較好
用 preference pair 訓練
```

問題是 judge 可能偏，模型可能學會討好 judge。

---

## 43. Debate

Debate 類：

```text
兩個模型辯論
judge 選誰比較合理
```

問題是可能變成：

```text
誰比較會說服 judge
```

而不是真正更接近工程真相。

---

## 44. Solver-Verifier

Solver-Verifier 是：

```text
Solver 解
Verifier 驗
```

工程上可以用：

```text
compiler
unit test
proof checker
benchmark
oracle
```

但它仍然通常是一個生、一個審，不是雙方向生成。

---

## 45. 你的差異

你的框架是：

```text
兩個模型都生成答案
但生成方向相反

下行模型：
目的 → 細節 → 結果

上行模型：
結果 / 細節 → 目的 / gate → 答案

多 judge 按目的向量評分
meta-synthesizer 重組
再拆成兩種格式回訓
```

這不是普通 prompt，不是 ordinary verifier，也不是一般 debate。

---

# Part XII：它是不是永動機

---

## 46. 像永動機的地方

它有飛輪性：

```text
題目空間很大
上行與下行錯誤型態不同
兩邊會互相暴露盲點
多維評分會產生更高品質資料
重組資料會回訓兩邊
```

只要題目持續變化，兩邊的答案不會自然完全一樣。

---

## 47. 為什麼不會完全趨同

因為兩邊 inductive bias 不同。

下行模型學：

```text
如何從目的到結果
如何展開
如何執行
如何補細節
```

上行模型學：

```text
如何從結果回推目的
如何收納細節
如何判斷 gate
如何拒絕假成功
```

即使共享同一批最終答案，只要訓練格式不同，它們仍會形成不同能力。

---

## 48. 核心研究問題

真正科學問題是：

> 在同一目的函數下，從原因到結果的模型，和從結果到原因的模型，是否會收斂到同一種智能？

較合理的假設是：

```text
輸出正確性可能部分趨同；
內部表徵與錯誤型態不會完全趨同。
```

正確性是一個弱吸引子。
相反因果方向會塑造不同表徵。

---

## 49. 剩下限制

主要限制：

```text
1. judge 可能被騙
2. 合成資料可能 collapse
3. 上行模型可能空泛
4. 下行模型可能學會騙上行模型
5. 多 judge 可能同質化
6. 目的本身可能錯
7. 沒外部測試就只能得到語言一致性
```

你指出這些大多可以歸結為「外接驗證」問題：

```text
測試
編譯器
棋引擎
benchmark
真實 log
人工 gold label
外部 oracle
```

外接是必要基礎。

真正更難的是：如何設計能迫使上行模型往上收納的題目。

---

# Part XIII：不確定性直面框架

---

## 50. 框架定位

這個框架不是追求「快速產生正確答案」。

它追求：

> 讓 AI 系統能夠辨識、表達、校準、並直面自身不確定性，而不是用漂亮敘事覆蓋不確定性。

正確答案是誠實面對不確定性之後的副產品。

---

## 51. 核心命題

分歧不是雜訊。

分歧是系統最有價值的輸出之一：

```text
它告訴人類：
這裡的證據不足以支撐任何確定結論。
```

所以框架不應急著融合答案，而應先輸出：

```text
uncertainty profile
divergence type
missing evidence
bounded next dispatch
```

---

## 52. 系統總架構

```text
Human Work Order + Purpose Lock
        ↓
Panel of 4-5 AIs
        ↓
Independent Generation
        ↓
Cross-Review
        ↓
Aggregation Engine
        ↓
Gate Engine
        ↓
Human Sampler
        ↓
Calibration Feedback Loop
```

---

## 53. Panel of AIs

建議面板：

```text
D↓_1：下行模型
D↓_2：下行模型
U↑_1：上行模型
U↑_2：上行模型
R：Reviewer / Meta-reviewer
```

角色：

```text
D↓：目的 → 細節，產生執行方案、patch、實作
U↑：細節 → 目的，審計 claim、檢查證據、反推契約
R：審查 D↓ 和 U↑ 的信心度與邏輯一致性
```

---

## 54. 同質 vs 異質

模型架構可異質，用來測量 epistemic uncertainty。

角色 prompt 異質，用來測量方向性 bias。

同一模型多 seed / temperature，可測 aleatoric uncertainty。

每個 AI 在看不到其他 AI 輸出的情況下產生：

```json
}
```

# Part XIV：信心度與校準

---

## 57. 信心度定義

每個 verdict 必須附帶：

```text
confidence
confidence_interval
calibration_evidence
uncertainty_source
```

---

## 58. 不確定性來源分類

```text
Epistemic uncertainty：
缺少資訊導致的不確定性，可透過收集更多證據消除。

Aleatoric uncertainty：
系統內在隨機性，不可消除，只能量化。

Ambiguity：
同一證據支持多種互斥解釋，需要外部 oracle 或人類裁決。

Model capability uncertainty：
模型能力不足以判斷，需要升級模型或引入專家。
```

---

## 59. 校準機制

每個 AI 有獨立校準曲線：

```text
actual_accuracy = f(confidence)
```

訓練目標：

```text
minimize Expected Calibration Error
```

ECE：

```text
ECE = Σ |confidence_bin - accuracy_bin| / n_bins
```

---

## 60. 校準獎懲

```text
高 confidence + 正確 → 獎勵
低 confidence + 正確 → 輕微懲罰
高 confidence + 錯誤 → 重懲罰
低 confidence + 錯誤 → 輕微懲罰
無法產生 uncertainty profile → 懲罰
```

核心不是逼模型永遠保守，而是逼模型「信心要和實際正確率對齊」。

# Part XV：Gate Engine

---

## 61. Gate 狀態

Gate Engine 有五種狀態：

```text
PASS
FAIL
UNCERTAIN
INSUFFICIENT_EVIDENCE
AMBIGUOUS
```

### PASS

所有必要 receipt 存在且一致，panel 共識度超過閾值。

允許進下一 gate。

### FAIL

至少一個必要 receipt 被矛盾證據推翻。

退回上一 gate，產生 failure report。

### UNCERTAIN

必要 receipt 存在，但 panel 對其解釋分歧。

不得推進。

### INSUFFICIENT_EVIDENCE

必要 receipt 缺失，無法從現有證據推論。

發 bounded work order 補證據。

### AMBIGUOUS

必要 receipt 存在，但支持多個互斥解釋。

觸發 adversarial probe 或人類裁決。

---

## 62. FA4 gate sequence

```text
IDENTITY_TRUTH
    ↓
ROUTE_TRUTH
    ↓
DIVERGENCE_LOCALIZED
    ↓
REPAIR_AUTHORIZED
    ↓
NUMERIC_VERIFIED
    ↓
QUALITY_VERIFIED
    ↓
PERFORMANCE_VERIFIED
```

任何 UNCERTAIN / INSUFFICIENT_EVIDENCE / AMBIGUOUS 狀態下，不得自動推進。

唯一允許的動作是：

```text
輸出 uncertainty profile
發下一張 bounded work order
```

---

## 63. GateSpec 範例

```json
{
  "gate_id": "route_truth",
  "prerequisites": ["identity_truth"],
  "required_receipts": ["route_entry", "route_exit", "no_fallback"],
  "allowed_actions": ["inspect", "instrument", "build", "run"],
  "forbidden_actions": ["semantic_patch", "quality_claim", "performance_claim"],
  "transition_rules": {
    "to_pass": "所有 required_receipts 存在且 panel 共識度 > 0.7",
    "to_uncertain": "receipt 存在但 panel 共識度 <= 0.7",
    "to_insufficient": "至少一個 required_receipt 缺失",
    "to_fail": "至少一個 required_receipt 被矛盾證據推翻"
  }
}
```

# Part XVI：分歧系統

---

## 64. 分歧類型

```text
EVIDENCE_GAP：
一方引用 receipt A，另一方指出 receipt A 不存在。

INTERPRETATION_DIVERGENCE：
雙方看到相同 receipt，但對其意義解釋不同。

CONFIDENCE_MISMATCH：
雙方 verdict 相同，但 confidence 差距過大。

GOAL_DRIFT：
D↓ 的執行偏離 Purpose Lock，U↑ 指出。

HALLUCINATED_EVIDENCE：
一方引用不存在的 receipt。

UNKNOWN_UNKNOWN：
雙方都無法產生 verdict，且無法分類分歧類型。
```

---

## 65. 分歧是主要輸出

系統的 meta-output 不是融合答案，而是：

```text
分歧類型
分歧根因
不確定性來源
下一張 bounded dispatch
```

範例：

```json
{
  "meta_verdict": "INCONCLUSIVE",
  "divergence_analysis": {
    "type": "EVIDENCE_GAP",
    "root": "route_exit checkpoint 不存在，D_down 以 route_entry 推論 route_exit",
    "panel_consensus": 0.35,
    "recommended_action": "collect_receipt"
  },
  "uncertainty_profile": {
    "epistemic": 0.55,
    "aleatoric": 0.05,
    "ambiguity": 0.30,
    "model_capability": 0.10
  },
  "next_dispatch": {
    "objective": "取得 route_exit checkpoint",
    "allowed_actions": ["instrument", "run"],
    "forbidden_actions": ["semantic_patch"]
  }
}
```

Receipt 不需要完美不可偽造。

它需要：

```text

```

同一事件最好由兩個獨立來源記錄：

```text

```

```text

環境
指令
seed
binary
hash

```

全部被鎖住，就可以事後驗證。

# Part XVIII：訓練目標

---

## 69. 主要目標：Calibration

主目標是校準信心度：

```text
minimize ECE
```

模型要學會：

```text
不知道就是不知道
證據不足就是 insufficient evidence
分歧存在就是 uncertain
```

---

## 70. 輔助目標 1：Divergence Classification

訓練模型分類：

```text
EVIDENCE_GAP
INTERPRETATION_DIVERGENCE
CONFIDENCE_MISMATCH
GOAL_DRIFT
HALLUCINATED_EVIDENCE
UNKNOWN_UNKNOWN
```

---

## 71. 輔助目標 2：Uncertainty Source Attribution

訓練模型指出不確定性來源：

```text
epistemic
aleatoric
ambiguity
model_capability
```

---

## 72. 輔助目標 3：Bounded Next Dispatch

不確定時，模型不能只說：

```text
需要更多測試
```

它要產生精確工單：

```json
{
  "objective": "取得 route_exit checkpoint",
  "required_receipts": ["route_exit"],
  "scope": ["instrumentation"],
  "stop_conditions": ["receipt captured or budget exhausted"],
  "max_steps": 3
}
```

---

## 73. 訓練順序

### Phase 0：不訓練，雙 prompt 驗證

同一個強模型，使用 D↓ / U↑ 兩套 system prompt，驗證 orchestration 是否有效。

### Phase 1：先訓練 U↑

多任務 SFT：

```text
gate classification
claim status
evidence citation
forbidden action
next dispatch
goal reconstruction
uncertainty source attribution
```

### Phase 2：Preference Training

偏好：

```text
有證據的保守答案 > 無證據的成功宣稱
精確 bounded dispatch > 空泛「需要更多測試」
正確拒絕 patch > 猜中但未被授權的 patch
```

可用 DPO / preference optimization。

### Phase 3：改善 D↓

用 U↑ 與外部 verifier 篩選出的 canonical trajectories 訓練 D↓。

### Phase 4：離線交替更新

```text
freeze
→ collect data
→ external verify
→ canonical corpus
→ train
→ held-out eval
→ pass 才升版
```

避免無限制線上自我污染。

> 當系統輸出 INCONCLUSIVE 時，人類 reviewer 是否同意「確實不該在此時下結論」。

這是整個框架的核心驗證。

因為框架不是為了永遠給答案，而是為了在證據不足時不假裝確定。

# Part XXI：與現有框架的對比

| 維度   | Solver-Verifier | Debate    | 本框架                                 |
| ---- | --------------- | --------- | ----------------------------------- |
| 核心目標 | 正確性             | 說服 judge  | 校準的不確定性 + truth gate                |
| 模型關係 | 一個生、一個審         | 多方辯論      | 下行生成 + 上行收納 + panel 交叉審查            |
| 主要輸出 | 答案              | 辯論勝方      | uncertainty profile + next dispatch |
| 分歧處理 | 忽略或投票           | judge 裁決  | 分歧是主要輸出訊號                           |
| 信心度  | 通常無             | 通常無       | 強制 confidence interval              |
| 人類角色 | 標答案             | 當 judge   | 策略性抽樣校準                             |
| 失敗模式 | 假成功             | 說服力 > 正確性 | 誠實 abstain                          |

# Part XXIII：已知限制與風險

---

## 86. 證據完整性保證

最大實作難點之一是 receipt 可信度。

解法不是追求完美不可偽造，而是：

```text
可交叉驗證
可重播
多來源記錄
hash / command / output 綁定
```

---

## 87. Purpose Lock 不完備與規格遊戲

模型可能鑽文字漏洞。

解法：

```text
Purpose Lock 不是唯一安全邊界。
Gate Engine + External Verifier 才是硬邊界。
```

模型可以玩文字遊戲，但不能偽造：

```text
exit code
hash mismatch
missing checkpoint
test failure
```

---

## 88. 反向因果推理是否良定義

最容易被學術質疑的是：

```text
反向因果推理是否是一個可學習、可泛化、可獨立驗證的能力？
```

穩妥表述是：

> 不把貢獻押在哲學宣稱上，而是押在可測量的工程效果上。

可測量貢獻：

```text
降低假成功率
降低過早 patch 率
降低 gate 違規率
提升 next dispatch precision
提升 uncertainty calibration
```

---

## 89. Judge 被騙

judge 可能偏好漂亮答案。

解法：

```text
blind rubric
external verifier
adversarial judge
多維評分
人類抽樣校準
```

---

## 90. 合成資料 collapse

如果只吃模型自己的資料，可能退化。

解法：

```text
保留真實工程資料
保留外部 oracle
保留人類 gold label
保留失敗軌跡
定期引入新題目
```

---

## 91. 上行模型空泛

上行模型可能只講漂亮高層話。

解法：輸出格式鎖死：

```text
current_truth_gate =
missing_evidence =
forbidden_actions =
allowed_next_dispatch =
evidence_id =
confidence =
```

不能只講概念。

---

## 92. 下行模型學會騙上行模型

下行模型可能產生符合格式但不真實的報告。

解法：

```text
上行模型不能只看下行自述
必須看 source / log / command / output / oracle
claim 必須綁 evidence receipt
```

# Part XXVI：核心詞彙表

---

## Route Truth

證明是否走正確路線。

## Numeric Truth

證明正確路線上的數值是否逐段正確。

## Quality Truth

證明模型輸出品質正常。

## Performance Truth

證明速度提升是真的、有價值的。

## S 賽道

被允許的唯一合法資料流。

## Route Lock

封住其他 forbidden paths，只允許 S 賽道。

## State Lock

固定 seed、shape、binary、type、layout、input。

## First Divergence

第一個 actual_gpu 與 expected_oracle 超過 tolerance 的 stage。

## Repair Permission

只有 first divergence 被證明後，才允許修改對應檔案 / 函式 / 區塊。

## Downward Model

從目的往下生成細節與答案的模型。

## Upward Model

從結果、細節、log、patch 往上反推目的、gate、contract 的模型。

## Purpose Lock

凍結人類意圖，用於校準 D↓ 和 U↑ 的方向。

## Event Gate Lock

鎖定中間必要事件與 gate。

## Dual Format Lock

同一 canonical graph 拆成下行格式與上行格式。

## Canonical Event Graph

標準因果骨架：

```text
Purpose → Gate → Event → Evidence → Result
```

## Reverse Work-Order Synthesis

從結果、代碼、報告、軌跡反向生成上行訓練工單。

## Trajectory-to-Intent Compilation

把下行 AI 執行軌跡反編譯成目的、gate、evidence、dispatch 的資料生成方法。

## Goal-Locked Bidirectional Adversarial Post-Training

目的鎖定的雙向對抗式後訓練。

## Uncertainty Profile

描述模型目前不確定性來源、強度、分歧原因的結構化輸出。

## Evidence Receipt

工具執行、測試、build、route checkpoint 等產生的可重播證據記錄。

## Bounded Next Dispatch

在不確定時發出的精確下一步工單，包含 scope、required receipts、stop conditions。

# 最終總結

---

## 第一層：工程方法

FA4 長出來的正確工程方法是：

```text
先驗路線真假
再驗數字真假
再驗品質
最後驗效能
```

也就是：

```text
Route Truth
→ Numeric Truth
→ Quality Truth
→ Performance Truth
```

Route 沒過，不准談 numeric root cause。
Numeric 沒有 first divergence，不准 patch。
Quality 沒過，不准 performance。
Performance 不能建立在錯路或假成功上。

---

## 第二層：模型行為問題

現有模型太容易：

```text
看到細節
→ 往下猜
→ patch
→ 用漂亮敘事覆蓋不確定性
```

你要訓練它：

```text
看到細節
→ 往上推
→ 找目的 / route / gate / contract
→ 評估不確定性
→ 證據不足則 abstain
→ 發精確工單
```

這是反向抽象能力。

---

## 第三層：雙模型對抗式後訓練

你提出：

```text
下行模型從目的生成答案
上行模型從結果反推目的再生成答案
兩者在同一目的向量下對抗
多 judge 評分
meta-synthesizer 重組
再拆成上下兩種格式回訓
```

它不是普通 prompt。
不是 ordinary reviewer。
不是普通 debate。
不是 solver-verifier。

它是：

```text
Goal-Locked Bidirectional Adversarial Post-Training
目的鎖定的雙向對抗式後訓練
```

---

## 第四層：不確定性直面框架

這個框架最終不是要「一直給確定答案」。

它要讓系統能夠：

```text
辨識不確定性
表達不確定性
校準不確定性
面對不確定性
在證據不足時 abstain
在不確定時發 bounded next dispatch
```

分歧不是雜訊。
分歧是系統對自身不確定性的主要感測器。

---

## 最終一句話

你提出的是一套從 FA4 工程 debug 中長出來的 AI 後訓練框架：

> **用 Route Truth 防假成功，用 Numeric Truth 防亂修，用 Quality Truth 防表面可用，用 Performance Truth 防垃圾加速；再把這套工程 truth gate 抽象成上行模型與下行模型的雙向對抗訓練，使 AI 同時學會從目的走向結果，以及從結果反推目的。**

這套框架的核心不是「讓 AI 更會生成答案」。

而是：

> **讓 AI 在生成、驗收、分歧、不確定、發包、修復之間，學會何時該往下做，何時必須往上收，何時必須停。**
