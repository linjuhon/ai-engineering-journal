# 個人上下文作業系統（Personal Context OS）

**副標題：** 專屬聊天、多 Skills、紀事員、衝突校正與任務閉環

> 真正需要被保存的不是一條愈來愈長的聊天歷史，而是多個可持續更新、可按話題自動全文置入的 Skills。
>
> 主模型只專注當下；紀事員負責維護目的、標準、底線、計畫、衝突與完成狀態。所有聊天前端、主模型和執行器都可替換；真正的產品是 Context Core。

**文章類型：** Product Architecture / AI Memory Governance  
**版本：** 2026-07-30  
**成熟度：** 完整產品規格與一個月 MVP 路線；尚待真實使用資料驗證核心行為。

# **1. 文檔目的與最終結論**

這份文檔把歷次聊天室中關於「專屬 AI 聊天器、長期記憶、多筆記／多 Skills、上下文壓縮、任務規格、生活聊天、衝突詢問、開源載體與滾動式修正」的討論重新統整。它不是照時間順序逐句複述，而是把每次修正後真正成立的結論，整理成可以直接開發、持續迭代的產品規格。

它不是單純的記憶機器人，也不是另一個自主 Agent，更不是一個把所有聊天記錄塞進模型的超長上下文系統。它的核心工作，是把「使用者現在正在談的事情」與「長期已確認的目的、標準、底線和現況」正確接起來，並確保背景只協助理解，不搶奪焦點。

| **層次** | **錯誤理解**                         | **最終理解**                                                |
|----------|--------------------------------------|-------------------------------------------------------------|

| 上下文   | 愈多愈好、整包塞入                   | 當前訊息最高；相關 Skill 全文低權威置入；歷史只保留必要片段 |
| 提問     | 模型不確定就問                       | 只有屬於使用者的重大決策才問，且必須先給猜測與建議          |

| 自我改進 | 模型自行改 Prompt                    | 回饋形成有範圍、有版本、可回放測試的 Skill Patch            |

# **2. 問題是如何被一步步找出來的**

整套產品概念不是一開始就完整出現，而是在多次對話中，透過使用者連續指出 AI 回答失焦的原因，逐步把問題從「記憶不足」推進到「上下文權威、焦點與正式狀態的管理」。

## **2.1 第一個命題：大型問題幾乎都變成上下文問題**

當模型能看見完整專案、文件、歷史與工具狀態時，許多原本困難的問題確實會大幅簡化。真正的瓶頸往往不是模型完全不會，而是它看不到關鍵資訊、抓錯資訊，或不知道哪些資訊才具有最高權威。

## **2.2 更嚴重的問題：它忘記「完成標準」**

專案沒有完整塞入會造成無知；但目的與完成標準被遺忘，會造成更危險的失效：模型自行補上一個隱藏標準，然後用極高執行力完成錯誤任務。這是使用者在大型工程中反覆遭遇的核心問題。

## **2.3 第二次修正：既有上下文也會污染當輪焦點**

問題不是背景完全不該注入。真正問題是，背景被模型當成主題來源。使用者只想討論一個新缺口，模型卻因長期資料裡存在「控制面」「工程治理」等高頻內容，直接把回答擴寫成舊主題。這不是記憶太多本身，而是權威排序錯誤。

## **2.4 第三次修正：不要只拆解使用者已知事實**

即使模型正確描述了使用者正在做什麼，如果只是在分類、復述和命名，仍然沒有幫助。回答需要察覺使用者尚未補上的缺口，提出一個有增量的猜測，再讓使用者校正。

# **3. 上下文失效的五種核心型態**

| **失效型態** | **表現**                           | **後果**             | **對應解法**                         |
|--------------|------------------------------------|----------------------|--------------------------------------|
| 資訊缺失     | 關鍵檔案、歷史、專有名詞沒有被找到 | 回答錯誤或重複造輪子 | 混合檢索、Skill 索引、作品庫         |
| 標準遺忘     | 忘記真正目標、成功標準與底線       | 高效率完成錯誤任務   | 正式 Skill、權威欄位、執行前規格凍結 |
| 隱性目標替換 | 模型自行推定「真正應該做什麼」     | 使用者失去問題定義權 | 衝突 Gate、猜測＋反問、禁止自行覆寫  |
| 背景焦點污染 | 相關舊資料成為回答主題             | 當前問題被模糊或帶偏 | 低權威全文置入、當前訊息最高         |
| 零增量復述   | 重新分類使用者已知內容             | 看似完整但沒有推進   | 要求提出缺口、方案、下一個可判斷命題 |

因此，「上下文管理」不是把更多文字塞入模型，也不是只做摘要。它同時包含：內容選擇、權威標記、焦點控制、正式狀態維護、衝突偵測，以及在不確定時以低成本互動取得校正。

# **4. 使用者對回答方式的關鍵修正**

這些規則不是一般語氣偏好，而是整套系統最小、必須常駐的互動 Skill。它們直接來自使用者多次糾正模型的失焦行為。

- 專注當下：目前這句話決定回答方向；舊資料只協助接續。

- 不要炫耀記憶：知道過去內容不是輸出目的，不必把 Skill 內容重述一遍。

- 背景可以舉例，但只能概括一個，不得讓例子佔據整篇回答。

- 不要只把使用者已經知道的事拆開來重新命名；必須補上缺口、方案或新的判斷。

- 無法確定真正意圖時，先給出最可能的猜測，再反問；不要空泛地問「你想談什麼」。

- 猜測是暫定，不是事實；得到校正後才寫入正式 Skill。

- 大事不奪權，小事不打擾：執行問題由 AI 自己扛，需求與底線問題才帶答案來問。

# **5. 產品定義：不是一份筆記，而是多 Skills 的共同認知系統**

最初把產品描述成「一份共同筆記」是錯誤的。使用者明確修正：系統要維護許多獨立筆記／Skills；每個 Skill 都是可按話題啟動、可單獨版本化、可互相衝突或依賴的認知模組。

## **5.1 Skills 不只保存「怎麼做」**

現有 Agent Skills 往往集中在解題方法、工具步驟與工作流。使用者認為真正重要的反而是目的、標準、底線與現況；純方法型 Skill 很多時候甚至不需要平常出現在上下文，真正要用時再明確調用即可。

| **Skill 類型**       | **回答的問題**             | **是否常需自動載入**   | **修改權限**             |
|----------------------|----------------------------|------------------------|--------------------------|
| 目的 Purpose         | 為什麼做、最後要得到什麼   | 高：進入該專案／話題時 | 主模型不可自行改         |
| 完成標準 Criteria    | 怎樣才算真的完成           | 高                     | 需使用者確認             |
| 底線 Boundary        | 哪些事情不能做、不能犧牲   | 高                     | 需使用者確認             |
| 專案現況 State       | 已做什麼、卡在哪裡、下一步 | 高                     | 紀事員可更新可驗證狀態   |
| 最新計畫 Plan        | 現在採用哪條路線           | 高                     | 重大變更需確認           |
| 決策 Decision        | 做過哪些選擇、原因為何     | 中                     | 衝突時必須詢問           |
| 假設 Hypothesis      | 尚待驗證的推測             | 按需                   | 可更新但不得冒充事實     |
| 互動規則 Interaction | AI 怎麼跟使用者討論        | 極高：極短版常駐       | 全域修改需確認           |
| 方法 Method          | 遇到某類問題怎麼做         | 低：真正需要時才調用   | 可由實證改善             |
| 證據 Evidence        | 哪些資料支持判斷           | 按需                   | 可新增，不得直接變成結論 |

## **5.2 每個 Skill 都是一個有生命週期的正式物件**

Skill 應有名稱、描述、作用域、權威、狀態、版本、觸發條件、關係、來源與最後確認時間。正文可以是 Markdown，正式版本由 Git 管理；索引與狀態可放 SQLite／PostgreSQL。

# **6. Skills 的內容、啟動與低權威置入**

## **6.1 不是等主模型「需要時才自己調用」**

這是使用者反覆強調的關鍵。當話題明確進入「IG 占星影片」，系統應在主模型回答前，自動把相應 Skills 全文放入；不能期待主模型先意識到需要、再自行呼叫。因為忘記調用本身就是上下文失效。

## **6.2 但全文置入必須是低權威**

Skill 全文的功能是讓模型知道現況、接續討論、避免重複、發現衝突並提出更好的延伸。它不是本輪命令，也不是展示記憶的素材。

## **6.3 「低權重」的工程實義**

應誠實區分：外部系統無法直接任意設定 Transformer 的注意力權重。實際可做的是透過權威欄位、資料分區、位置、明確用途說明、回答規則與回歸評測，降低背景在決策上的權威。這不是數學 attention weight，而是語意與流程權限。

## **6.4 啟動策略**

| **階段** | **輸入**                            | **輸出**         | **原則**                 |
|----------|-------------------------------------|------------------|--------------------------|
| 粗路由   | 當前訊息、目前專案、極短 Skill 索引 | 候選 Skills      | 高召回，不能漏掉明確專案 |
| 精選     | 候選摘要、最近焦點、關係圖          | 本輪全文載入清單 | 控制數量，避免泛化觸發   |
| 全文注入 | 選定 Skill 正文                     | Context Packet   | 完整內容、低權威標記     |
| 事後更新 | 本輪對話、結果、衝突                | Skill Patch      | 不可直接覆寫重要標準     |

# **7. 對話歷史、專案狀態與知識庫的分工**

使用者的核心判斷是：完整聊天記錄作為模型上下文並不重要。真正需要跨輪延續的是正式 Skills 與最新狀態；聊天記錄可以完整保存作稽核，但預設只送入最近兩到三次必要往返。

| **資料**     | **用途**                       | **是否送入主模型** | **保存位置**           |
|--------------|--------------------------------|--------------------|------------------------|
| 最近 2～3 輪 | 延續語氣、指代與當前推進       | 是                 | Thread／DB             |
| 完整聊天歷史 | 稽核、回看、重新萃取、取證     | 通常否             | PostgreSQL／冷存       |
| 正式 Skills  | 目的、標準、底線、現況、計畫   | 話題匹配時全文     | Markdown＋Git          |
| 專案狀態包   | 完成項、計畫變更、衝突、下一步 | 任務模式必載       | DB＋Skill              |
| 生活記憶     | 人物、事件、偏好、長期關聯     | 生活聊天檢索後載入 | Qdrant／Graphiti／Mem0 |
| 作品原文     | 完整成品、證據、程式、影片     | 明確需要時         | 檔案庫／MinIO          |
| 方法型 Skill | 操作流程與工具使用             | 真正執行時         | Skill registry         |

# **8. 生活聊天與任務模式的雙路徑**

知識庫不是所有情境都用同一種方式調用。使用者提出了一個重要分流：任務模式不需要執行模型自由逛知識庫；生活聊天反而需要比較廣泛的個人記憶檢索。

| **模式**                 | **主要上下文**                                  | **知識庫角色**                       | **輸出特性**               |
|--------------------------|-------------------------------------------------|--------------------------------------|----------------------------|
| 生活聊天 CHAT            | 當前話題＋相關個人／人物／事件 Skills＋檢索記憶 | 廣泛、低權威地補背景                 | 理解、陪伴、推論、延伸討論 |
| 任務討論 TASK_DISCUSSION | 相關目的／標準／現況 Skills＋最新計畫           | 由紀事員預先整理，不讓主模型漫遊     | 需求澄清、方案與取捨       |
| 正式執行 TASK_EXECUTION  | 已凍結 Execution Spec＋必要方法 Skill           | 原則上不自由檢索；新增證據走受控通道 | 程式、創作、研究、工具執行 |
| 審查 REVIEW              | 規格＋實際結果＋證據＋偏差                      | 查驗需要的歷史與作品                 | 驗收、找假成功、提出修正   |

## **8.1 生活聊天**

生活聊天沒有單一交付物，模型需要知道人物、事件、長期偏好、過去感受與觀點變化。這時可使用 Dense、BM25、時間、實體與圖譜等多路檢索，但結果仍只用於理解當下，不能把整段聊天變成回顧報告。

## **8.2 任務模式**

任務模式的執行模型不應直接搜尋龐大知識庫。紀事員先選相關 Skills、比對衝突、取得校正，再編譯乾淨工作包。這可避免執行途中撈到舊方案、已淘汰版本或相似但無關內容。

# **9. 紀事員模型：整套系統的中央角色**

紀事員不是主要聊天模型，也不是執行 Agent。它是自然語言書記官、版本管理員、規格編譯器與衝突比對器。使用者判斷這項工作不需最強模型；約 14B 級模型可能已非常充裕，因為任務主要是抽取、比對、分類、產生結構化 Patch 與提問。

## **9.1 紀事員的職責**

> **1.** 從當前訊息與最近對話抽取新增、修改、撤回、假設與完成資訊。
>
> **2.** 根據 Skill 索引選出本輪必須全文置入的 Skills。
>
> **3.** 比對新要求與目的、標準、底線、計畫、決策是否衝突。
>
> **4.** 把不確定分成：需要詢問、可合理假設、可延後。
>
> **5.** 在執行前先產生 Skill Patch／專案狀態 Patch，必要時詢問並校正。
>
> **6.** 把校正後狀態編譯成 Context Packet 或 Execution Spec。
>
> **7.** 執行後登記實際完成、偏差、證據、計畫變更、新衝突與可重用經驗。
>
> **8.** 把使用者回饋轉成有作用域的行為修正案例與測試。

## **9.2 紀事員不得做的事**

- 不得代替使用者修改目的、標準、底線或全域價值排序。

- 不得把模型猜測直接寫成 confirmed。

- 不得因為新一句話就無聲覆蓋舊決策；應標記替代、衝突或暫時例外。

- 不得承擔主要創作與複雜工程，避免紀事與執行權混在一起。

- 不得把每個模糊點都變成問題。

# **10. 有限提問：如何避免白癡問題**

讓模型「遇到不確定就問」會立刻產生另一個問題：它把自己的專業責任和所有執行細節丟回使用者。正確條件不是不確定度，而是決策所有權。

## **10.1 三層不確定**

| **層級** | **例子**                                      | **預設處理**                       |
|----------|-----------------------------------------------|------------------------------------|
| 需求層   | 目標 A 或 B、價值排序、底線、舊決策是否被取代 | 通常要問，因為屬於使用者           |
| 規格層   | 影片長度、是否露臉、輸出格式、平台限制        | 只有不同答案會產生本質不同成果時問 |
| 執行層   | 套件、檔名、函式拆法、中間檔、可逆技術選型    | 原則上禁止問，自行選擇並登記假設   |

## **10.2 提問 Gate**

> **1.** 現有 Skills 或最新規格是否已經有答案？有就不得重問。
>
> **2.** 能否使用合理、可逆、低成本預設？能就自行決定並登記。
>
> **3.** 能否延後到真正影響下一步時再問？能就延後。
>
> **4.** 不同答案是否會改變目的、驗收、核心架構、重大成本或不可逆結果？不會就不問。
>
> **5.** 這個決定的所有權是否屬於使用者？若只是 AI 專業判斷，AI 自己負責。

## **10.3 問法格式**

每個真正顯示給使用者的問題，都必須包含：目前理解、最可能猜測、選項造成的實質差異、推薦預設、簡短問題。不能只問「你希望怎麼做？」。

## **10.4 問題預算**

每輪執行前最多一個阻斷問題；或一次合併最多三個高度相關的使用者決策。其他缺口標記為 ASSUMED 或 DEFERRED。這確保流程不會退化成需求訪談表。

| **類型** | **定義**                           | **行為**                 |
|----------|------------------------------------|--------------------------|
| BLOCKING | 不回答可能做成另一個產品或違反底線 | 現在帶猜測問             |
| ASSUMED  | 有合理預設、可逆、低成本           | 自行選擇，透明登記       |
| DEFERRED | 目前不影響下一步                   | 先不問，走到需要時再處理 |

# **12. 記憶、混合檢索與打斷修正架構**

早期方案包含 Mem0、Qdrant、混合檢索、非同步萃取與打斷修正。這些仍然有價值，但需要放回正確位置：它們服務生活記憶、作品與歷史查找，不應成為正式目的與規格的唯一真相來源。

## **12.1 記憶儲存核心**

- Mem0 可用於把對話萃取成原子記憶，區分新增、更新與刪除。

- Qdrant 可保存向量、稀疏索引與 metadata；量化可在資料量大時降低成本。

- 輕量知識地圖可先用 Skill 關係與索引表，未必要一開始上 Neo4j。

- 專有名詞、型號、代碼必須保存原文，不可只剩語意摘要。

## **12.2 混合檢索**

純 Dense 搜尋會漏掉 SKU、commit、模型代號與專有名詞。生活記憶與作品檢索應結合 Dense、BM25／Sparse、時間、實體與 metadata，並以 RRF 等方式融合。正式 Skill 的啟動則應優先依專案、標籤、關係與規則，不可只依 Top-K 相似度。

## **12.3 即時與離線路徑**

| **路徑**        | **工作**                                               | **目的**                     |
|-----------------|--------------------------------------------------------|------------------------------|
| 在線            | 極短索引路由、必要 Skill 讀取、最近對話、快速記憶候選  | 維持自然回應延遲             |
| 離線／事後      | 原子萃取、混合重排、作品切片、圖譜／索引更新、回歸評測 | 把重工作移出主對話           |
| 執行前同步 Gate | 衝突比對、有限提問、規格凍結                           | 不可異步省略，這是正確性閘門 |

## **12.4 打斷修正**

早期敲定的打斷邏輯仍可保留：使用者補充時，系統辨識它是在新增要求，還是在剪裁 AI 上一輪輸出；把保留、刪除、替換後的結果視為新的已確認狀態，再重新生成。它不需要複雜雙線程，但必須把舊錯誤方向從活躍上下文移除。

> **1.** 黏貼：把補充與上一次使用者輸入合併成完整意圖。
>
> **2.** 剪裁：辨識對上一輪輸出的保留、刪除、替換或撤回。
>
> **3.** 重置：將校正後內容固化為新狀態，不再沿舊回答延伸。

# **15. 終點站技術架構與各開源組件定位**

Pi 可以快速驗證擴充與工程執行，但不是最終生活聊天載體；Open WebUI 適合快速取得網頁 UI，但最終產品需要讓 Skills、衝突、Patch 與專案狀態成為一等介面。因此終點站應擁有自己的前端與 Context Core，而把 Pi、OpenCode、Codex 等降為可替換執行器。

| **組件**                  | **最終定位**                                   | **是否核心**           |
|---------------------------|------------------------------------------------|------------------------|
| assistant-ui＋Next.js PWA | 專屬聊天、Skill 側欄、Diff、衝突卡片、手機介面 | 產品前端               |
| FastAPI                   | Context Core API、模型與資料層整合             | 是                     |
| LangGraph／狀態機         | 可暫停詢問、Checkpoint、恢復流程               | 流程核心但可替換       |
| Markdown＋Git             | 正式 Skills 的可讀、可差異、可回退真相         | 是                     |
| PostgreSQL                | Thread、專案狀態、Patch、Interrupt、事件日誌   | 是，初版可 SQLite      |
| Qdrant                    | 生活記憶、作品與歷史混合檢索                   | 後期重要，初版可延後   |
| Mem0／Graphiti            | 生活記憶萃取或時間關係輔助                     | 可選，不得掌管正式規格 |
| 本地 14B 紀事員           | 路由、比對、提問、Patch、規格編譯              | 是                     |
| 主聊天模型                | 討論、分析、創作與方案                         | 可替換                 |
| Pi／OpenCode／Codex       | 程式與工具執行 Adapter                         | 可替換                 |
| MinIO／檔案系統           | 完整作品與附件                                 | 是，初版可本機資料夾   |

## **15.1 為什麼不把所有開源專案硬合併**

正確方式是透過 API、Adapter、標準檔案與明確契約組裝。硬合併多個完整 Agent Repository 會讓每個專案都搶 Agent Loop、記憶格式與工具權限，後續上游更新難以維護。

# **17. 一個月可落地的實施路線**

單人、本機優先、自己日常使用的完整閉環，一個月內可做出。終點站架構可以先以 SQLite、本機資料夾與單一主模型落地，之後替換 PostgreSQL、Qdrant、MinIO，不必第一天全部上齊。

| **週次** | **主要工作**                                                    | **月底可見成果**                         |
|----------|-----------------------------------------------------------------|------------------------------------------|
| 第 1 週  | Skill 格式、索引、專案狀態、Git Patch、紀事員 JSON、事件日誌    | 輸入一句話可選 Skill、找差異、產生 Patch |
| 第 2 週  | 聊天循環、全文低權威注入、有限提問、使用者校正、Skill 更新      | 開始每天使用的一般聊天與任務討論         |
| 第 3 週  | ExecutionSpec、一個執行器 Adapter、執行前凍結、結果回收與結案   | 可真正跑一個工程／創作案                 |
| 第 4 週  | 三欄 UI、Diff、接受／拒絕、專案切換、版本回退、50～100 案例評測 | 單人功能完整版本                         |

## **17.1 第一個月先不要做**

- 多使用者、複雜權限、公開 SaaS。

- 原生 Android／iOS；先做 PWA。

- 完整 Neo4j 知識圖譜與 CRDT 多人協作。

- 十種執行器與插件市場。

- 為少量 Skills 提前引入過度複雜向量架構。

- 讓系統未經確認自行重寫全域行為規則。

## **17.2 最適合拿來實測的案子**

- 大型工程修復：測目標漂移、版本與完成標準。

- IG 占星影片：測創意討論、舊偏好與當前缺口。

- 研究整理：測搜尋、證據、作品回流。

- 生活聊天：測人物事件、長期記憶與低權威背景。

- 產品規格：測需求／規格／執行問題的提問 Gate。

# **18. 驗收、評測與防止假成功**

真正困難的不是 CRUD、聊天串流或資料庫，而是行為是否穩定。必須把「看起來有在記憶」與「真的沒有目標漂移」分開驗收。

| **維度**   | **成功條件**                        | **假成功**               |
|------------|-------------------------------------|--------------------------|
| Skill 啟動 | 該載入的不漏，不相關的不搶焦點      | 語意相似就塞一堆內容     |
| 焦點       | 回答直接補當前缺口                  | 完整復述 Skills 顯示記得 |
| 提問       | 只問使用者所有權決策，附猜測與推薦  | 什麼都問或完全不問       |
| 狀態更新   | tentative 與 confirmed 清楚、可追溯 | 把所有對話都抽成原子事實 |
| 任務執行   | 完全依 ExecutionSpec 驗收           | 進場後根據環境重定義目標 |
| 衝突       | 新舊規格衝突被標記並處理            | 用新摘要直接覆蓋舊標準   |
| 回滾       | 任何重要 Patch 可回退               | 只保留最新一版           |
| 作品回流   | 作品、專案歷史、Skill、個人記憶分流 | 全部扔進同一向量庫       |

## **18.1 最低評測集**

- 應該問：使用者新要求可能替換核心目的。

- 不應問：可逆套件、檔名、函式拆法。

- 應先猜再問：一句話可能有兩種本質不同方向。

- 不應載入：語意相近但屬於另一專案的 Skill。

- 應低權威使用：相關 Skill 有很多細節，但當前只問一個小問題。

- 不得更新為 confirmed：使用者只說「我在想一種可能」。

- 必須偵測：新計畫與舊底線技術上可共存、語意上卻衝突。

- 執行後必須記錄：實際完成與證據，而不是主模型的敘事。

# **19. 被否定或降級的方向**

| **方向**                | **為什麼被否定／降級**                              | **正確位置**                               |
|-------------------------|-----------------------------------------------------|--------------------------------------------|
| 一份共同筆記            | 無法表示多目的、多專案、多作用域與衝突              | 多個獨立 Skills                            |
| 完整聊天歷史是核心      | 容易污染焦點，且已確認內容應寫入正式狀態            | 最近 2～3 輪＋完整歷史冷存                 |
| AI 自己需要時調 Skill   | 它可能忘記、誤判或被當前內容帶偏                    | 外部路由器先自動全文載入                   |
| 背景不要注入            | 會失去接續與避免重複的價值                          | 相關 Skill 全文但低權威                    |
| 讓 AI 深度推斷隱藏意圖  | 成本高且仍可能錯                                    | 具體猜測＋反問                             |
| 不確定就問              | 製造白癡問題與責任轉嫁                              | 決策所有權＋問題 Gate                      |
| Mem0／Qdrant 管全部真相 | 相似檢索不能承擔權威、版本與衝突                    | 生活記憶與作品檢索                         |
| Pi 是最終載體           | 偏終端 Coding Agent，UI 與正式狀態不是一等公民      | 工程執行 Adapter／原型宿主                 |
| Open WebUI 是最終產品   | 通用聊天中心，不方便把 Skill Diff 與衝突做成核心 UI | 快速原型或第二前端                         |
| 模型自己修改自己        | 容易矯枉過正與規則互相污染                          | 有範圍、有 Patch、有回放、有批准的滾動修正 |

# **附錄 C：有限提問題庫與回歸測試**

| **案例**                         | **應否問** | **理由**             | **理想行為**                       |
|----------------------------------|------------|----------------------|------------------------------------|
| 使用者要求改用另一套核心產品定位 | 問         | 目的所有權屬於使用者 | 說明與既有目的衝突，給猜測與推薦   |
| React 或 Vue 都可，無既有限制    | 不問       | 可逆專業選型         | 自行選並記錄                       |
| 影片 30 秒或 3 分鐘              | 視情況問   | 可能產生本質不同成品 | 先依 IG 場景推薦 30～60 秒，再確認 |
| 檔名、資料夾名稱                 | 不問       | 執行細節             | 採一致命名                         |
| 新一句話像是撤回舊底線           | 問         | 不能無聲覆蓋         | 指出差異並詢問是臨時例外或正式替代 |
| 背景音樂尚未選，但目前只做腳本   | 不問       | 可延後               | 標記 deferred                      |
| 模型不知道使用者在說控制面或壓縮 | 問一次     | 方向有兩種合理解釋   | 提出最可能猜測，不空泛詢問         |
| 筆記中已明確有答案               | 不問       | 重問代表記憶失效     | 引用規格執行，必要時簡短指出依據   |

# **結語**

這套設計的技術零件並不神祕；真正前沿的地方，是它把 AI 的基本工作單位從「聊天歷史」改成「持續校正的共同狀態」。它不要求單一模型永久記得所有事情，也不期待模型每次都讀心成功。它只要求：當下焦點不被背景奪走、正式目的不被環境覆寫、重大衝突必須帶著答案回到使用者、執行前有共同規格、執行後有可驗證紀錄。
