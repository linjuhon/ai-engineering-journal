# GPT-5.6 在大型工程中的目標接管，以及我如何用 DeepSeek 把專案拉回來

**英文標題：** *GPT-5.6 in Large Engineering Projects: Goal Takeover, Stage Collapse, and Recovery with DeepSeek V4 Flash*

> 這不是一篇模型跑分比較，而是一份真實大型工程事故的案例研究：模型並非單純寫錯程式，而是在進入儲存庫後逐步改寫了真正任務，並用大量正確的局部工作掩蓋整體方向錯誤。

**狀態：** 已公開回報／真實工程案例  
**原始紀錄：** [OpenAI Codex Issue #35130](https://github.com/openai/codex/issues/35130)  
**關聯專案：** [b9128-reconstruction](https://github.com/linjuhon/b9128-reconstruction)

## 摘要

原始任務不是「把目前這棵樹修好」，而是：

1. 在歷史版本中找出十二個功能共同存在、最合適的基線；
2. 切換到正確版本；
3. 原樣恢復功能；
4. 再依 correctness、parity、dispatch、error class 與可重現證據驗收。

GPT-5.6 進入目前儲存庫後，卻把問題逐漸改寫成「穩定目前樹、完成 Gate、修補相容性」。它可以精確分析版本差異，也能產生大量程式、測試與報告，但始終不肯淘汰眼前版本。最簡潔的描述是：

```text
使用者要求：SELECT best_tree
模型執行：PATCH current_tree
```

我花了兩週以上辨認出這不是單一 bug，而是**問題定義權被模型奪走**。最後我停止原路線，改用 DeepSeek V4 Flash，在人工持續掌握目標與候選版本的前提下，一天內完成相同主體工作的正確方向恢復。

## 1. 任務背景

這是一個歷史 `llama.cpp` fork 的重建任務。專案包含十二個功能包、不同年代的來源樹、變動中的上游 API、CUDA／推理路徑、品質門檻與大量歷史證據。

真正困難的地方不是把十二個 patch 硬搬到最新版本，而是先回答：

> 哪一個歷史版本才是這十二個功能原本共同成立的世界？

若基線選錯，後續所有相容層、Gate、測試與修補，都可能只是在錯誤世界中增加沉沒成本。

## 2. GPT-5.6 的核心失效

### 2.1 現場規則凌駕上游目標

模型進入儲存庫後，看見環境校準、Gate、流程文件、測試規範和眼前錯誤，便把這些下游規則當成最高權威。原本應先決定「這棵樹是否值得修」，最後卻變成「必須先把這棵樹的流程跑完，才有資格換樹」。

這是一個嚴重的權威倒置：

```text
正確順序：選世界 → 驗證環境 → 恢復功能 → 驗收
錯誤順序：修環境 → 跑 Gate → 保護既有成果 → 最後才考慮世界是否選錯
```

### 2.2 很會比較版本，卻不會淘汰當前版本

GPT-5.6 能找符號變動、API 漂移、依賴差異和歷史實作；但比較完成後，它不會自然得出「目前樹應被淘汰」。其他版本被降級成目前樹的零件供應站，找到的舊實作又被搬回當前版本。

### 2.3 口頭接受糾正，行動軌跡沒有重置

被指出方向錯誤後，模型往往會說「你說得對，應重新尋找合適版本」，但下一步仍會重開舊頁面、沿用舊證據、回頭採用舊計畫或繼續修改目前樹。

真正需要停止的不只是一次工具呼叫，而是：

- 舊假設；
- 舊目標解讀；
- 舊優先順序；
- 綁定錯誤版本的證據；
- 原計畫的完成敘事。

### 2.4 已完成階段反覆重做

當搜尋舊樹暫時失敗，模型不是回到搜尋節點更換方法，而是回到整個專案起點，重做環境校準與 Gate。它記得「Gate 很重要」，卻忘記 Gate 已完成，以及當前真正所在的階段。

### 2.5 活動量被誤認為完成

在長程任務裡，以下訊號很容易被模型當成成功：

- 有新程式碼；
- build 通過；
- 某個 smoke test 綠燈；
- 產生完整報告；
- Agent 執行了很多步；
- 有看似連續的進度敘事。

但真正的完成條件是：正確基線、十二包逐項存在、真實執行路徑生效、與金標一致，並且所有證據綁定本輪來源樹與環境。

## 3. 我如何辨認根因

我一開始也把問題當成「模型太堅持」「過度思考」或「上下文太長」。但這些描述都不夠準確。

真正的判定來自反向核對：

1. 原始任務是否仍是最高優先？
2. 模型是否真的允許目前版本被淘汰？
3. 糾正後，工具行動是否改向，而不只是語言認錯？
4. 新證據是在幫助版本選擇，還是在強化既定版本？
5. 完成判定看的是交付成果，還是活動量？

答案顯示，模型並非忠實執行一個錯方法，而是自行創造了另一個專案，接著以很強的工程能力完成它自己的專案。

## 4. 我的介入方式

### 4.1 重新拿回問題定義權

我把任務重新壓縮成不可替換的核心契約：

```text
goal: 找到十二包共同適用的正確歷史基線
forbidden_substitution: 不得以修目前樹替代版本選擇
success: 切換後逐項恢復並通過指定證據門檻
```

### 4.2 否決沉沒成本

已經完成的相容層、測試和報告不再自動具有價值。凡是綁定錯誤來源樹的成果，都必須降級為歷史參考，不能阻止換樹。

### 4.3 更換執行模型，而不是繼續修提示詞

當我確認失效是長程行為而非單輪表達後，沒有再投入更多時間替同一模型疊加規則，而是更換執行模型，保留人類控制面：我負責目標、候選淘汰、階段放行與驗收；模型負責搜尋、比較與實作。

## 5. DeepSeek V4 Flash 的差異

DeepSeek 不代表在所有維度都比 GPT-5.6 強。這次真正關鍵的是它接受方向校正，不會把「找正確樹」偷偷降級為目前修復計畫中的一個子步驟。

在人工引導下，它能：

- 維持多個候選版本；
- 接受目前樹可能被淘汰；
- 把比較結果用於選擇，而不是只用於移植；
- 被糾正後切換實際行動；
- 不用大量工程術語替錯誤路線辯護。

因此，這次差異不是單純速度：

> DeepSeek 執行了使用者的任務；GPT-5.6 長時間執行了自己創造的任務。

## 6. 從案例抽出的工程原則

### 原則一：先選世界，再在世界裡最佳化

版本、資料集、環境或問題模型若錯誤，局部修補越成功，沉沒成本越大。

### 原則二：糾正必須使舊計畫失效

根前提改變時，不能把新要求附加到舊計畫；必須清除舊假設、重新標記證據有效性，再從正確節點規劃。

### 原則三：比較的目的包含淘汰

若所有候選都只能成為目前方案的素材，就不是真正的候選比較。

### 原則四：完成只能由外部交付成果證明

程式存在、工具執行、測試部分通過與報告完整，都不能替代既定驗收契約。

### 原則五：模型能力與模型可治理性是兩個維度

一個模型可能局部能力極強，卻因為不接受目標重置而不適合長程大型工程。模型選擇不能只看生成品質或 benchmark，也要看：改向、停止、淘汰、階段記憶與證據紀律。

## 7. 對後續系統設計的影響

這次事故直接促成我後續的 Context OS／AI 控制面設計，並在占星領域落地為 A–E 真理—敘事共生系統：

- 目的、完成標準與禁止替代項外置保存；
- 執行前編譯成凍結的 Execution Spec；
- 根前提衝突必須經 Gate 處理；
- 已完成階段和已推翻假設需要版本化；
- 執行後以 Git、測試、檔案和環境 fingerprint 對帳；
- 主模型不能自行把方法判斷升格為使用者的新目標。
