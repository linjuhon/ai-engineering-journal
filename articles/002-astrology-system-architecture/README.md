# 第一篇　系統定位與架構原則

## 1. 系統目標

系統接受出生時間與地點，計算行星、宮位、相位與特殊天體點，再從知識庫與案例庫取回證據，使用 AI 生成個人化詮釋，最後進行行運／推運等預測並輸出報告。架構同時追求低延遲、可追蹤、可擴展、可回復與文檔自動同步。

## 2. 四項核心原則

- **階段為主：** 每個階段有明確輸入、輸出、時限、責任模塊、監控與錯誤策略。

- **單一事實來源：** 所有派生文件由統一主文檔產生，禁止在生成文件上直接維護架構真相。

- **跨階段公共服務：** 標籤、資料與運維能力不複製到每個業務階段，而以接口供應。

- **品質與技術債前置：** 大文檔、配置密集、代碼塊密集與多技術棧內容，在輸入時就被辨識並套用不同品質規則。

## 3. 邏輯分層

| 層級 | 包含階段／模塊 | 主要責任 |

| --- | --- | --- |

| 交互與安全層 | Stage 1–3；02、08、00、06、09 | 輸入、驗證、授權、解析、標準化 |

| 核心計算層 | Stage 4–5；01、00、06、09 | 天文位置、宮位、相位與格局 |

| 知識與智能層 | Stage 6–7；03、04、06、09 | 檢索、案例、AI 詮釋、個人化 |

| 預測與交付層 | Stage 8–9；05、07、08、02、06、09 | 預測、量化、報告、API 與檔案輸出 |

| 工程治理層 | 10、09、文檔處理器 | CI/CD、容器、監控、品質與文件同步 |

# 第二篇　端到端數據流

## 5. 雙模式處理策略

即時模式負責讓使用者快速知道「資料是否可用、身份是否有效、系統將如何計算」；完整模式負責重型計算、知識、AI、預測與報告。兩種模式應共享 requestId、traceId、版本與狀態機，使用者可以先取得 accepted／validated 回應，再串流接收進度與完整結果。

| 模式 | 階段 | 原稿總目標 | 推薦語義 |

| --- | --- | --- | --- |

| 即時模式 | 1–3 | <350ms | 同步完成，回傳驗證與任務識別 |

| 完整模式 | 4–9 | <5,500ms | 非同步／串流完成；應重新閉合總預算 |

| 並行優化 | 4 與 6 | 節省 200ms、提升 28.6% | 僅適用不依賴最終天體／相位結果的預取部分 |



## 6. 建議的標準處理封包

每個階段都應接收與回傳統一的處理封包，避免資料只存在某個服務的臨時物件中：

```text
ProcessingEnvelope {
  requestId, traceId, userId, stage, status,
  inputVersion, schemaVersion, algorithmVersion, modelVersion,
  startedAt, finishedAt, processingTimeMs,
  payloadRef, resultRef, qualityScore, confidence,
  warnings[], errors[], provenance[]
}
```

原稿已分散包含 requestId、processingTime、timestamp、version、qualityScore 等欄位；重整版將其提升為全流程契約。這是由原稿元素歸納出的統一方案，仍需在接口規格中正式定案。

# 第三篇·Stage 1　用戶輸入階段

## 1.1 階段定位與時限

**目標時限：** < 100ms　　**所屬模式：** 即時模式

接收出生資料、地點、時區與輸出偏好，完成格式驗證、標準化及初始風險預檢，讓後續階段只處理結構化且可追蹤的資料。

## 1.2 輸入資料

- 出生日期（YYYY-MM-DD，原稿設定 1900–2100）

- 出生時間（HH:mm:ss）

- 緯度（-90～90）與經度（-180～180）

- IANA 時區識別符

- 可選地名、宮位制、相位容許度、輸出格式與使用者偏好

## 1.3 核心處理流程

1. 格式驗證：必填欄位、型別、日期／時間格式、座標範圍、時區識別符。

2. 格式標準化：日期轉 ISO 8601、時間轉 24 小時制、座標統一六位小數、時區名稱標準化。

3. 錯誤分類：INVALID_DATE_FORMAT、INVALID_TIME_FORMAT、INVALID_COORDINATES、INVALID_TIMEZONE、MISSING_REQUIRED_FIELD。

4. 初始標籤化與資料存放：標籤系統、資料管理、監控服務並行處理。

5. 技術債預檢：文件規模、配置密度、程式碼區塊數、技術棧數量與品質風險等級。

## 1.4 輸出與責任邊界

- ValidatedInput / ProcessedInput

- requestId 與處理時間

- 標準化出生資料與初始標籤

- 儲存位置、驗證分數、錯誤或警告

**參與模塊：** 主要：02-API服務、08-用戶服務；支援：00-標籤系統、06-數據管理、09-系統運維

**資料策略：** PostgreSQL 儲存結構化輸入；Redis 保存會話與短期驗證快取；MongoDB／Elasticsearch 保存元資料、標籤與檢索索引。

## 1.5 主要接口／服務

- POST /api/v1/charts/validate-input

- POST /api/v1/charts/quick-validate

- POST /api/v1/charts/batch-validate

- WebSocket validate:realtime / validate:batch

- GraphQL validateInput / validateField / standardizeInput

## 1.6 性能與品質門檻

- 總處理 <100ms

- 驗證準確率 >99.9%

- 吞吐量 >1,000 req/s

- 錯誤率 <0.1%

- 技術債預防準確率 >95%

- 品質風險預測準確率 >90%

## 1.7 錯誤與恢復

輸入問題應即時回饋並引導修正；網路錯誤可重試三次後降級；系統錯誤需保留 requestId、階段、堆疊與處理時間。

## 1.8 原稿差異與待決策

原稿同時出現 Ant Design 與 Material-UI v5 兩套前端 UI 標準；重整版保留此差異，應在實作前由架構決策統一。

# 第三篇·Stage 5　相位計算階段

## 5.1 階段定位與時限

**目標時限：** < 300ms　　**所屬模式：** 完整模式

從天體黃經建立行星對、計算最短角距、識別有效相位與容許度，並評估強度、應用／分離狀態及複合格局。

## 5.2 輸入資料

- PlanetaryPositions

- 宮位與尊貴資訊

- OrbSettings / AspectTypes

## 5.3 核心處理流程

1. 生成全部行星配對並計算 0–180° 最短角距。

2. 依合相、對分、三分、四分、六分及次要相位定義判斷容許度。

3. 計算 exactness、行星尊貴、宮位位置、相位性質等強度因子。

4. 識別大三角、T 三角、大十字、Yod、群星等複合模式。

5. 相位標籤化、關係圖存放、統計與監控。

## 5.4 輸出與責任邊界

- AspectCalculationResult

- ValidAspect[]

- AspectWithStrength[]

- CompositePatterns

- AspectStatistics

**參與模塊：** 主要：01-天體計算引擎；支援：00-標籤系統、06-數據管理、09-系統運維

## 14. 總時限閉合問題

原稿的階段上限合計為 6,200ms；若 Stage 4 與 6 完全重疊，理論上只減少 200ms，仍為 6,000ms。因此「完整模式 <5,500ms」不能由目前數字推出。可採下列其中一種正式定義：

- 各階段數值是獨立 worst-case，總體 5,500ms 是典型 p95，兩者不直接相加；必須提供實測分布。

- Stage 8 為可選或延後工作，完整本命分析不含預測；預測另開任務。

- Stage 7 與 8 某些子任務並行，或 Stage 9 先流式回應再產檔。

- 把完整模式門檻修正為 <6,000ms，並重新設定各階段預算。

在性能定義閉合前，不應以「已達 <5,500ms」作驗收結論。

## 15. 統一錯誤模型

| 等級 | 原稿處理 | 重整後要求 |

| --- | --- | --- |

| Critical | 立即停止後續階段 | 保留完整上下文、觸發熔斷／回退，不可輸出成功 |

| Medium | 記錄後繼續 | 輸出 degraded 狀態與受影響功能，不得隱藏 |

| Low | 僅記錄 | 保留 warning 與來源，允許正常完成 |



通用恢復機制包括 circuit breaker、graceful degradation、automatic retry、fallback mode。每次重試需有 idempotency key、最大次數、退避策略與錯誤分類，避免把邏輯錯誤無限重試。

## 16. 安全基線

- JWT 簽名、過期、撤銷與會話一致性；秘密不得硬編碼，需輪替與最小權限。

- RBAC 之外仍需資源所有權與資料範圍檢查。

- 輸入清理、速率限制、異常模式偵測、敏感資料遮罩與審計日誌。

- 傳輸與靜態資料、備份及日誌均需加密並套用敏感度規則；文件生成流程同時掃描秘密、個資與不應公開的內部配置。

## 19. 複雜度觸發條件

## 20. 零技術債的正確定義

「零技術債」應是生產放行門檻，而不是自我宣告。至少要同時具備：所有標記可配對、無重複 canonical 區段、生成結果可重現、內容一致性檢查通過、未解問題有明確 owner／期限／風險，且任何豁免均被版本化。原稿本身的重複與破碎證明它尚未達成這個狀態。

# 第八篇　自動化文檔管理

## 21. 單一事實來源與標記系統

主文檔以 HTML 註釋標記 Stage、責任、模塊、跨階段服務、技術實作、性能與實施計畫。處理器解析這些區段，生成 12 個模塊的派生文檔、9 個階段文檔、公共服務與聚合視圖。生成文檔必須標示「禁止直接編輯」與來源版本。

| 標記類型 | 示例 |

| --- | --- |

| 完整階段 | <!-- STAGE_01_COMPLETE_START --> … <!-- STAGE_01_COMPLETE_END --> |

| 階段責任 | <!-- STAGE_01_RESPONSIBILITIES_START --> |

| 階段模塊 | <!-- STAGE_01_MODULES_START --> |

| 技術實作 | <!-- STAGE_01_TECHNICAL_IMPLEMENTATION_START --> |

| 公共服務 | <!-- TAG_SYSTEM_SERVICE_START --> / DATA_MANAGEMENT / SYSTEM_MONITORING |

| 聚合視圖 | <!-- MODULE_MATRIX_START --> / PERFORMANCE_SUMMARY / IMPLEMENTATION_STATUS |



## 22. 文檔處理器流程

- 解析主文檔並建立抽象結構。

- 驗證標記配對、唯一性、嵌套與必要章節。

- 並行生成模塊文件、階段文件、公共服務與聚合視圖。

- 對生成結果執行內容一致性、連結、性能數值與技術棧檢查。

- 比較 Git diff；生成結果未提交或與來源不同步時阻止合併。

CLI 原稿包括 `astrology-doc-processor generate`、`validate`、`--dry-run` 與 `--strict`。模板引擎採 Handlebars，處理器以 TypeScript／Node.js 實作。

## 23. CI/CD 文件工作流

- 觸發：主文檔或 document-processor 變更、Pull Request、定時檢查。

- Validate：結構、標記、交叉引用、內容一致性。

- Generate：48 個模塊文件、9 個階段文件及聚合文件。

- Diff：若產物與來源不同步則失敗，要求本地重新生成。

- Deploy：主分支驗證通過後構建文檔站點與搜索索引，可部署 GitHub Pages。

- 版本：語義化版本；main／develop／feature／release 分支；至少兩人審批。
